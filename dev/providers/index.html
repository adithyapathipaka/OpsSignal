    Providers¶

    A provider delivers a signal to one destination. Configure each one under providers in signal.yaml, then name it in a route. Keep credentials out of the file with ${VAR} or a secret reference such as ${aws-sm:prod/opssignal#pd_key} (see Configuration).

    Provider Key Required fields Optional fields
    Console console none enabled
    Slack slack webhook_url none
    Webhook webhook url none
    PagerDuty pagerduty routing_key url
    Microsoft Teams teams webhook_url none
    Opsgenie opsgenie api_key url, tags
    Email email from, to, and smtp.host or ses cc, subject_prefix, smtp.port, smtp.username, smtp.password, smtp.tls, ses.region, ses.configuration_set

    All providers are in the base package. The one exception is email through the Amazon SES API, which needs opssignal[aws]; email over SMTP, SES's SMTP endpoint included, needs no extra.

    A route's providers are tried in order and delivery stops at the first one that succeeds, so later providers are fallbacks, not extra copies. A route providers: [pagerduty, teams] pages through PagerDuty and posts to Teams only if PagerDuty could not be reached. Any non-2xx response or connection error is a failed attempt; each provider gets up to 3 attempts with backoff.

    Console¶

    Prints one line per signal to stdout. It is always registered, because unmatched signals fall back to it, and cannot be turned off.

    Slack¶

    providers:
  slack:
    webhook_url: "${SLACK_WEBHOOK_URL}"

    Posts the title, message and a severity emoji to a Slack incoming webhook.

    Webhook¶

    providers:
  webhook:
    url: "https://alerts.example.com/opssignal"

    POSTs the full signal as JSON, with every field of the signal model.

    PagerDuty¶

    providers:
  pagerduty:
    routing_key: "${PAGERDUTY_ROUTING_KEY}"
    # EU-hosted accounts only:
    # url: "https://events.eu.pagerduty.com/v2/enqueue"

routes:
  - match:
      severity: [critical]
      environment: prod
    providers: [pagerduty, slack]

    Triggers an alert through the Events API v2. routing_key is the integration key of an Events API v2 integration on a PagerDuty service (Service > Integrations > Add integration). url defaults to https://events.pagerduty.com/v2/enqueue.

    How a signal maps to the event:

    PagerDuty field From the signal
    dedup_key dedup_key (the core computes one from source, event type, title and environment if the caller gives none), cut to 255 characters
    payload.summary title, cut to 1024 characters
    payload.source source
    payload.severity severity; success becomes info
    payload.timestamp timestamp
    payload.component component, if set
    payload.group service, if set
    payload.class event_type
    payload.custom_details signal_id, event_type, severity, and whichever of message, environment, team, run_id, correlation_id, trace_id and metadata are set
    links log_url, if set, as "Logs"

    Because the dedup key is stable, the same failure sent again adds to the open alert instead of paging a second time. OpsSignal only triggers alerts; it does not acknowledge or resolve them.

    Route only the severities that should wake someone to PagerDuty. A route that sends info signals there will page on them.

    Microsoft Teams¶

    providers:
  teams:
    webhook_url: "${TEAMS_WEBHOOK_URL}"

routes:
  - match:
      severity: [warning, error]
    providers: [teams]

    Posts an Adaptive Card to a Teams channel. Create the URL with the Workflows app: in the channel, choose Workflows > Post to a channel when a webhook request is received, and copy the URL it gives you. Legacy Office 365 connector incoming-webhook URLs accept the same message, but Microsoft is retiring them.

    The card shows:

    • the title, coloured by severity (red for error and critical, amber for warning, green for success);
    • the message, if set;
    • facts for severity, source and event type, plus environment, service, component, team and run ID when set;
    • a View logs button when log_url is set.

    Opsgenie¶

    providers:
  opsgenie:
    api_key: "${OPSGENIE_API_KEY}"
    # EU-hosted accounts only:
    # url: "https://api.eu.opsgenie.com/v2/alerts"
    tags: [data-platform]

routes:
  - match:
      severity: [critical, error]
      environment: prod
    providers: [opsgenie, slack]

    Creates an alert through the Alert API. api_key is the key of an API integration on the Opsgenie team that should receive the alert (Teams > your team > Integrations > Add integration > API). The team's routing rules and escalations decide who is notified. url defaults to https://api.opsgenie.com/v2/alerts.

    How a signal maps to the alert:

    Opsgenie field From the signal
    message title, cut to 130 characters
    alias dedup_key, cut to 512 characters
    description message, followed by a "Logs:" line when log_url is set
    priority severity: critical is P1, error P2, warning P3, info and success P5
    source source
    entity service/component, or whichever of the two is set
    tags the configured tags, then the severity and the environment, up to 20
    details signal_id, event_type, severity, timestamp, whichever of environment, service, component, team, run_id, correlation_id, trace_id and log_url are set, and each top-level metadata key as metadata.<key>

    Because the alias is stable, the same failure sent again raises the open alert's count instead of opening a second alert. OpsSignal only creates alerts; it does not acknowledge or close them.

    Atlassian is folding Opsgenie into Jira Service Management. Its operations alert API takes the same request, so a migrated team can point url at the endpoint shown on its JSM API integration and keep the rest of the config.

    Email¶

    providers:
  email:
    from: "OpsSignal <alerts@example.com>"
    to: [data-oncall@example.com]
    cc: [data-platform@example.com]     # optional
    subject_prefix: "[opssignal]"       # optional
    smtp:
      host: smtp.example.com
      username: "${SMTP_USERNAME}"
      password: "${SMTP_PASSWORD}"
      # tls: starttls (default, port 587) | tls (port 465) | none (port 25)
      # port: 2587

routes:
  - match:
      severity: [error, critical]
    providers: [slack, email]

    Sends a plain-text email through any SMTP server, or through the Amazon SES API with ses in place of smtp. The subject is <subject_prefix> [SEVERITY] <title>; the body has the message, the signal's fields (severity, source, event, environment, service, component, team, run ID, correlation and trace IDs, log URL), its metadata, and the signal ID and time.

    tls decides how the connection is secured:

    tls Default port Meaning
    starttls 587 Plain connection upgraded with STARTTLS. If the server doesn't offer it, the send fails rather than going out unencrypted.
    tls 465 TLS from the first byte (SMTPS).
    none 25 No encryption. Only for a relay on localhost or inside your network.

    username and password go together; leave both out for a relay that does not ask for authentication. Addresses are checked when the config loads, so a typo fails at startup instead of on the first alert.

    Every email for the same dedup_key carries the same References header and subject, so mail clients thread repeats of a failure into one conversation.

    Hosted email services all accept SMTP, so they need no extra package:

    Service smtp.host Credentials
    Amazon SES email-smtp.<region>.amazonaws.com SES SMTP credentials (SES console > SMTP settings)
    SendGrid smtp.sendgrid.net username apikey, password the API key
    Mailgun smtp.mailgun.org (smtp.eu.mailgun.org in the EU) the domain's SMTP login
    Postmark smtp.postmarkapp.com the server API token as both username and password
    Gmail / Google Workspace smtp.gmail.com the account and an app password, or use the Workspace SMTP relay
    Microsoft 365 smtp.office365.com a mailbox with SMTP AUTH enabled

    Amazon SES API¶

    providers:
  email:
    from: "OpsSignal <alerts@example.com>"
    to: [data-oncall@example.com]
    ses:
      region: eu-west-1               # optional; defaults to AWS_REGION
      configuration_set: alerts       # optional

    Sends through the SES v2 SendEmail API with the standard AWS credential chain: an EKS service account (IRSA), an ECS task role, an EC2 instance profile, or AWS_ACCESS_KEY_ID/AWS_SECRET_ACCESS_KEY. There are no SMTP credentials to store or rotate. The role needs ses:SendEmail on the sending identity, and from must be an address or domain verified in SES for that region (while the account is in the SES sandbox, so must every recipient). AWS_ENDPOINT_URL_SESV2 overrides the endpoint, for a VPC endpoint or LocalStack.

    This needs AWS support: pip install 'opssignal[aws]' for Python, or a CLI or C library built with --features aws. Without it, the config fails to load with an error naming the extra, rather than failing on the first alert. Set exactly one of smtp and ses. The message is the same one SMTP sends, threading headers included.

    Email is a slow channel: use it for the trail and for people who are not on chat, and pair it with an on-call provider for anything urgent. Because delivery stops at the first provider that succeeds, [email, slack] sends to Slack only when the email could not be handed to the server.
